# Decisions

| ID | Decision | Rationale |
|---|---|---|
| D-000 | The working title "NightNode" is renamed to Thirdshift | Aligns implementation, binaries, environment variables, and model IDs with the product name |
| D-001 | Product sells model access, not GPU rental | Keeps hardware invisible and aligns with downstream value |
| D-002 | Windows NVIDIA only for v0.1 | Matches reachable gaming-cafe supply and reduces compatibility surface |
| D-003 | llama.cpp and GGUF | Consumer hardware support and reduced arbitrary-code risk |
| D-004 | Outbound WebSocket | Avoids port forwarding, CGNAT, and public host endpoints |
| D-005 | Curated catalog | Preserves security, licensing, reliability, and liquidity |
| D-006 | Non-sensitive data only | Community nodes cannot guarantee host-blind confidentiality |
| D-007 | Central coordinator | Reliability and iteration before decentralization |
| D-008 | Dollar ledger, manual payout | Validates economics before payment automation and compliance work |
| D-009 | One job and one model per node | Simplifies memory, scheduling, and failure handling |
| D-010 | No streaming in v0.1 | Simplifies retries and response semantics |
| D-011 | Use a single Go module at the repository root | This deviates from handoff section 8.4's `go.work` example; one module is simpler for the current monorepo and keeps shared internal packages importable without workspace coordination |
| D-012 | Use a small internal migration runner built on pgx | Avoids adding a migration framework while still giving idempotent SQL application and checksum protection |
| D-013 | Use `github.com/santhosh-tekuri/jsonschema/v6` for schema tests | Provides draft 2020-12 JSON Schema validation with a small, focused dependency |
| D-014 | Use prefixed ULID-style sortable text IDs | Keeps IDs human-scannable by resource type while preserving chronological sorting and avoiding database-specific ID generation |
| D-015 | `thirdshift doctor` reports unsupported non-Windows hosts without failing the process | Lets macOS development and CI exercise the command while keeping Windows 11 x64 NVIDIA as the host target |
| D-016 | Pin llama.cpp release `b10180` for Milestone 1 | Current official release checked on 2026-07-29; macOS arm64 archive SHA-256 `789f717355fb2574becfaa70601714c78908bd1e5d6c6cadd6b8ccc98060d0f7` was downloaded and verified |
| D-017 | Pin Windows runtime artifacts from llama.cpp `b10180` as executable plus CUDA support archive | Official release splits Windows x64 CPU executable archive SHA-256 `55d092fa5cd85e996ac556d00f427b313267dc27a18f8eb3f6ad3530782d41e0` from CUDA 12.4 DLL archive SHA-256 `8c79a9b226de4b3cacfd1f83d24f962d0773be79f1e7b75c6af4ded7e32ae1d6`; both were downloaded and verified |
| D-018 | Runtime release manifests are Ed25519-signed over canonical JSON excluding the signature field | Keeps signature verification deterministic with only the Go standard library and avoids committing private signing material |
| D-019 | Pin `unsloth/SmolLM2-135M-Instruct-GGUF` Q2_K as `thirdshift-tiny-chat-v1` | Apache-2.0 model card metadata and 88,201,792-byte GGUF SHA-256 `c53fe6626c7165ebfd8de5db22edc3f719b813da001e662bc5cb453f2540a076` were verified from the pinned Hugging Face revision `9e6855bc4be717fca1ef21360a1db4b29d5c559a` |
| D-020 | The Milestone 1 tiny model uses `gpu_layers: 0` and `device: none` | Makes the macOS CPU demo path reliable while the doctor command still enforces Windows NVIDIA host eligibility for real hosting |
| D-021 | The model cache stores files as `<sha256>.gguf` and evicts by modification-time LRU | Content-hash addressing prevents name confusion; mtime gives a simple stdlib-only access signal and active model protection |
| D-022 | Use `nhooyr.io/websocket` v1.8.17 for node sessions | Provides a small, maintained WebSocket implementation with context-aware dial, accept, read, write, and close semantics |
| D-023 | Use HMAC-SHA256 stateless node access tokens for Milestone 2 | Keeps token issuance stdlib-only and lets the coordinator verify short-lived bearer tokens without another persistence table |
| D-024 | Use key-signed token refresh for invite-free re-login | A stored Ed25519 private key can request a fresh access token without reusing the single-use invite or bootstrap token |
| D-025 | Store node config as a minimal TOML file parsed with the standard library | Satisfies the host-readable config requirement without adding a YAML or TOML dependency during the alpha |
| D-026 | Store node private keys in 0600 local files for Milestone 2 and keep Windows Credential Manager as a compiling stub | Preserves restricted local storage now while isolating the Windows credential integration behind build tags for later implementation |
| D-027 | Use a Unix socket for local node control on non-Windows and a 127.0.0.1 control-port stub on Windows | Keeps pause, resume, and status behind a local-only control channel that remains cross-compilable before real Windows named-pipe work |
| D-028 | Use operator bearer auth from `THIRDSHIFT_OPERATOR_TOKEN` for internal coordinator endpoints in Milestone 2 | Keeps invite creation and node inventory protected until the operator console and account model exist |
| D-029 | Default reconnect backoff starts at 1 second and caps at 60 seconds with 20 percent jitter | Prevents tight reconnect loops while keeping recovery quick for a single alpha node |
| D-030 | Developer API keys use `tsak_` secrets with only `sha256:` hashes stored in PostgreSQL | The secret is shown once at creation while the coordinator can still authenticate bearer requests without storing recoverable API keys |
| D-031 | Model permissions are explicit per API key and created during `admin-cli apikey create` | Keeps P0 access control simple and testable before account and billing policy land |
| D-032 | `admin-cli catalog sync` loads valid local catalog manifests into the coordinator database and skips incomplete placeholder manifests | The repository still contains early placeholder manifests; P0 routing should sync the pinned tiny model without mutating read-only catalog files |
| D-033 | Public API rate limiting is an in-memory per-key fixed one-minute window for alpha | Satisfies abuse protection without adding Redis or another dependency; distributed limits move to a later production milestone |
| D-034 | Scheduler weights are loaded from coordinator config with defaults centralized in `internal/coordinator/jobs` | Keeps scoring deterministic in tests and configurable without scattering numeric weights across scheduling code |
| D-035 | Job results are signed with the node identity Ed25519 key over the `job.completed` payload excluding the signature field | Reuses the existing node trust root and lets the coordinator verify result integrity before accepting completion output |
| D-036 | CPU-class model hardware profiles may set `min_vram_mb = 0` | The local CPU demo model is legitimate supply for development and tests, so migration `000004` relaxes the original strictly-positive VRAM constraint to non-negative |
| D-037 | `thirdshift start --runtime-base-url` is a development-only loopback attach path | It enables the documented fake-runtime routed demo while preserving scheduler eligibility through catalog model and runtime hashes |
| D-038 | Host work schedules are local-time windows with start inclusive and end exclusive; equal start/end means always in window | This matches the host-facing mental model, handles overnight windows such as 23:00-08:00, and avoids storing timezone-specific recurring calendar data before M4 needs it |
| D-039 | Thermal recovery uses a configurable 5 C default hysteresis below the soft maximum temperature | Prevents rapid AVAILABLE/DRAINING oscillation around the configured temperature limit while keeping the host eligible again after meaningful cooling |
| D-040 | M4 transient failures retry exactly once on a different eligible node | Limits duplicate work and user-visible latency while proving the lease/result path before reputation and multi-retry scheduling arrive |
| D-041 | Coordinator and node structured logs use a shared stdlib `slog` redaction handler and log IDs instead of prompt or completion bodies | Keeps request, job, and attempt traceability while reducing the chance of leaking prompts, completions, API keys, invite tokens, or private material |
| D-042 | Accepted job results post one balanced microdollar ledger transaction inside the coordinator completion transaction | Couples customer charge, host pending credit, platform margin, result persistence, and job success so duplicate or replayed results cannot create extra credit |
| D-043 | Host credits move from pending to available through `admin-cli credits release`, with `THIRDSHIFT_CREDIT_HOLD_SECONDS` defaulting to 24 hours | Keeps the alpha hold process explicit and testable before a background payout/release worker exists |
| D-044 | Duplicate verification sampling is deterministic from the job id and per-model `duplicate_sample_rate` | Makes tests reproducible and avoids adding random scheduler state while preserving percentage-based sampling behavior |
| D-045 | Node-reported token counts are accepted only after coordinator plausibility checks | The runtime result is still node supplied, so malformed usage, impossible totals, and oversized completions are rejected before ledger credit; outliers are recorded as verification events |
| D-046 | Challenge quarantine requires repeated failures against an injected threshold; one disagreement never quarantines | Matches the handoff safety rule while allowing tests and future policy code to choose stricter or looser per-model thresholds |
| D-047 | Payout create/export/confirm and economics reports are direct database admin commands | Accounting operations need to work even when the HTTP coordinator is stopped; operator web workflows remain out of scope for Milestone 5 |
| D-048 | Use Next.js `15.5.21` with TypeScript `5.6.3` for the operator console | This line is fully supported by local Node `18.20.8` and avoids production advisories npm reports for the older Next 14 line |
| D-049 | The operator console stores the operator token only in `sessionStorage` | Keeps the alpha login simple while avoiding durable browser storage for the bearer secret |
| D-050 | The console talks to the coordinator with same-origin direct fetch behind Caddy | `/internal-console` and `/internal/v1` share one origin in deployment, so no browser CORS trust expansion is needed |
| D-051 | Fleet schedule defaults apply only when a node has no local schedule override | Fleet enrollment can set cafe-wide defaults, but host-local `thirdshift configure` settings and schedule env vars remain authoritative |
| D-052 | M6 alerts are computed from persisted coordinator state with configurable thresholds | The alpha console can surface operational risk without adding another alerting service before the pilot |
| D-053 | Console production dependency overrides pin patched `postcss` and `sharp` transitive versions | Keeps the Node 18-compatible Next line while avoiding known production dependency advisories in the generated lockfile |
| D-054 | Use Vitest `3.2.6` for console component tests | It is the current patched Vitest line that supports Node 18; Vitest 4 requires Node 20 or newer |
| D-055 | Reuse the signed runtime release-manifest shape for Thirdshift app updates | One Ed25519-signed artifact manifest format keeps installer, updater, and runtime verification code paths aligned |
| D-056 | `thirdshift update` retains the previous binary beside the active binary | Side-by-side rollback metadata is simple, cross-platform, and testable before a full Windows service updater exists |
| D-057 | Public `/v1/status` is cached in the coordinator for 10 seconds | Launch traffic can refresh the status page frequently without adding a cache service or hitting aggregate SQL on every request |
| D-058 | Contribution card JSON exposes only per-node aggregate stats | The share card can be public enough for launch while avoiding prompt, completion, account, payout, or hardware fingerprint data |
| D-059 | The console app serves without a Next.js basePath; Caddy maps both `/internal-console` and `/status` | Keeps `/status` a real public route while preserving the M6 internal console URL through proxy prefix stripping |
| D-060 | `make ps-check` uses PowerShell's parser when available and a Go structural fallback otherwise | macOS contributors can run a meaningful local check while CI still performs true PowerShell parsing on Windows |
| D-061 | Public catalog regions are nullable aggregate labels resolved as node override, then fleet default, then unknown | Gives operators enough control to show regional availability while preserving the guardrail against exposing node identities or per-host details |
| D-062 | `/v1/status` reads requester region only from a trusted proxy header configured by `THIRDSHIFT_REQUESTER_REGION_HEADER`, with `CF-IPCountry` as fallback | Avoids server-side IP geolocation and keeps visitor location hints under deployment control |
| D-063 | Public waitlist signup is unique-email idempotent and rate-limited in memory per remote IP | Developers can retry safely without leaking whether an address already exists, while alpha abuse protection stays dependency-free |
| D-064 | Catalog manifests may include an optional public `description`; absent descriptions fall back to `display_name` | Lets the public model catalog render one-line model copy without mutating existing read-only catalog manifests |
| D-065 | The public catalog is demand-first: models with no supply are listed as `listing.status: waitlist` and shown as "Available on request" | Demand is cheaper to test than supply, and a listed model with a pinned manifest becomes live the moment nodes come online with no further code change |
| D-066 | Public listing state lives in a new `models.listing_status` column, not in the existing `models.status` CHECK | `models.status` is the operational lifecycle that routing and scheduling filter on (`status IN ('alpha','active')`); overloading it would either make waitlist models routable by accident or make hidden models unroutable. Separate columns let `thirdshift-tiny-chat-v1` stay fully routable while disappearing from the public page |
| D-067 | Waitlist models never report node counts, regions, or measured speed; real supply always overrides the waitlist presentation | The honesty constraint for the public page. `/v1/status` only substitutes the `waitlist` availability state when no node is online with the model at all, so any real capacity falls through to the existing available/limited/offline logic untouched |
| D-068 | `thirdshift-tiny-chat-v1` is `listing.status: hidden` | It is a 135M smoke-test model for the routed request path, not a product. It stays synced, priced at zero, and routable for internal testing while the public catalog stops advertising it |
| D-069 | Waitlist model expected speeds are conservative single-stream estimates, not measurements, and are labeled "expected" in the UI | No node has run these models yet, so there is no median to publish. The manifest carries `listing.expected_output_tokens_per_second` (30 tok/s for the 7B Q4_K_M models, 60 for the 3B) as an estimate for the 8 GB NVIDIA floor class; the field is only rendered for waitlist rows |
| D-070 | Alpha prices sit below a manifest-recorded `market_comparison`, and the public page shows the comparison plus a discount rounded to the nearest 5 percent | Price is the reason to try a community network; the comparison makes that concrete without a live pricing feed. The tag is the average of the input and output discounts (25 percent and 20 percent for the Qwen models, so "~25% cheaper"), rounded half-up, and is suppressed entirely when a manifest carries no comparison or when we are not actually cheaper |
| D-071 | Host credit for the new models is 50 percent of the customer output price | Keeps the platform margin explicit and consistent across the catalog while the alpha economics are still being validated |
| D-072 | All three new manifests set `min_vram_mb: 8192`, including the 3B model | 8 GB is the platform floor: `eligible_gpu_classes` starts at `ts-nvidia-8gb-v1`, so advertising 4-6 GB would claim supply the scheduler cannot use |
| D-073 | The 8192-token alpha context is split as 7168 input plus 1024 output | Manifest limits can then never exceed the runtime context window, which a flat 8192 input limit plus 1024 output tokens would |
| D-074 | New GGUF pins are verified from the Git LFS pointer at a pinned commit, cross-checked against the `resolve` endpoint headers | `https://huggingface.co/<repo>/raw/<commit>/<file>` returns a small pointer whose `oid sha256` is the file content hash, and `x-linked-etag`/`x-linked-size` on the resolve redirect confirm it. Both sources agreed for all three files, so the hashes are verified without downloading 11 GB |
| D-075 | `llama-3.2-3b-instruct` ships with `license.reviewed_at: TODO-OPERATOR-REVIEW` | The Llama 3.2 Community License is not a standard OSI license and carries acceptable-use and attribution terms, so hosted serving stays blocked until the operator signs off |
| D-076 | The public waitlist form is a reviewed application: use case and a data-class acknowledgment are required, name and volume band are optional | Manual review needs the use case to judge data-class fit, and a recorded acknowledgment is the evidence the applicant saw the security boundary from handoff section 18.2 |
| D-077 | `waitlist_signups.model_id` is plain text with a length CHECK and no foreign key | The value arrives from an unauthenticated public form; a foreign key would turn a stale or hostile model id into a 500 instead of a reviewable row |
| D-078 | A repeat application gets the same answer as a new one | The public form no longer says "you are already on the list", so a submission cannot be used to probe which addresses have applied. The duplicate flag stays in the API response for the operator path |
| D-079 | The public `/status` page is a light minimalist theme scoped under `.public-page`; the operator console stays dark | They serve different audiences and the public page is the launch surface. Scoping every rule under `.public-page` plus a `body:has(.public-page)` background rule keeps the two themes from leaking into each other in one shared stylesheet |
| D-080 | Green is reserved for the live availability dot; every other state uses a neutral gray dot | A green dot is the strongest honesty signal on the page, so it only ever appears when nodes are actually serving the model right now |
| D-081 | The public repo flip should ship node plus protocol as open source while coordinator, console, and discovery stay closed | Hosts need to audit what runs on their machines and developers need the wire contract; scheduling, pricing, ledger, and operator surfaces are the business. This requires a repository restructure before the Milestone 7 flip, which is not yet done |
| D-082 | Access applications upsert on `(email, model_id)` instead of no-op inserting on `email` | The unique-email insert with `ON CONFLICT DO NOTHING` silently dropped every returning applicant's payload while still answering 200, so a better use case submitted later never reached the reviewer. Uniqueness per email and model also lets one person apply for several models, which the catalog invites |
| D-083 | The `(email, model_id)` unique constraint is `NULLS NOT DISTINCT` | A NULL `model_id` means "no specific model". Postgres treats NULLs as distinct by default, so without this two general applications from the same address would both insert and reintroduce the duplicate-row bug for every applicant who does not name a model. Requires PostgreSQL 15 or newer; deployment runs 16 |
| D-084 | Rows predating `model_id` keep NULL and become that applicant's general-application row | It is the honest reading of a v1 signup: they asked for access, not for a named model. No data is invented, and their next model-specific application creates a separate row rather than overwriting history |
| D-085 | `created_at` is the first application and `last_applied_at` is the latest; the reviewer queue sorts by `last_applied_at` | Reviewers want the freshest applications first, and keeping both timestamps shows whether someone has been waiting a while or just revised their answers |
| D-086 | `POST /v1/waitlist` no longer returns a `duplicate` flag | With upsert semantics the flag would mean "you have applied before", which is exactly the prior-state disclosure the public form must not make. The response is now identical for a first application and a resubmission, so it cannot be used to probe which addresses have applied |
| D-087 | Llama 3.2 Community License signed off 2026-07-30; compliance is manifest-driven | Operator reviewed the license (commercial hosted inference permitted below 700M MAU). Three mechanisms: a `license.attribution` manifest block renders "Built with Llama" plus the license notice and AUP link on public surfaces; `license.distribute_with_model: true` makes every node write the vendored agreement text next to the cached GGUF (fetch-from-Meta is impossible for nodes because the upstream repo is gated, so the text is embedded in the binary); model prep fails hard if distribution is required but no vendored text exists. Apache-2.0 models declare nothing and render nothing |
| D-088 | Public host identity is a deterministic adjective-animal handle derived from SHA-256 of the node id | The earnings ticker needs a stable name per machine across refreshes without exposing anything about it. Only 16 bits of the hash reach the output over a 64x64 name space, so a handle cannot be walked back to a node id; collisions are possible and harmless because the handle is a label, never a key the platform resolves by |
| D-089 | Host earnings are summed from `host_credit_holds`, not from `ledger_entries` | Holds carry `node_id` directly and hold exactly one row per accepted attempt, so a per-node sum needs no join through job_results and cannot double count a credit that has moved from pending to available. Reversed holds are excluded because that credit was not earned |
| D-090 | The ticker lists any node with a session in the last 24 hours, including offline ones | A machine that contributed earlier today is part of the story; hiding it the moment it sleeps would make the network look emptier than it is. State is reported honestly as serving, idle, or offline rather than omitted |
| D-091 | The public map is a committed dot-matrix land mask generated from Natural Earth 110m land polygons | Public domain source, rasterized offline by `scripts/generate-world-mask.mjs` into a 200x77 equirectangular bitmask so the page needs no map library, no tiles, and no network at build or run time. Latitude is cropped to 83N..56S because Antarctica spans every column and reads as a heavy bar rather than a quiet texture. Resolution is 200 columns so that at full-bleed width the cells stay a fine texture rather than a chunky mosaic |
| D-092 | Map heat is per region, spread over a neighbourhood sized from the grid width, with a darker core and lighter halo, capped at four steps | A region is the finest location the platform will ever disclose, and a single lone pixel reads as noise. The radius is derived from the mask width rather than fixed, so a region occupies the same share of the map at any resolution. The halo makes one node a soft smudge; the cap keeps a large region from turning into a black block |
| D-093 | The map is a full-bleed band above the wordmark, clipped rather than letterboxed | An equirectangular world is inherently about 2.6:1, so full width and a shallow band are in tension. A `max-height` alone letterboxes the SVG and leaves side gutters, which is not full width. Instead the SVG keeps its true aspect at 100% width and the container clips the tail, with the fade mask reaching full transparency before the clip line so the cut is invisible and only already-faded southern rows are lost |
| D-094 | Runtime re-pinned from llama.cpp b10180 to b10182 for a real Windows CUDA build | b10180 shipped no Windows CUDA asset at all, so the pinned `win-cpu-x64` binary had no CUDA backend compiled in. `--n-gpu-layers` was silently ignored and the first production node served every token on its CPU at 7.4 tok/s while its RTX 3060 Ti sat idle at 34W. b10182 ships `win-cuda-12.4-x64`. When pinning a runtime, verify the artifact's accelerator backend, not just that the release exists |
| D-095 | `gpu_layers` is an explicit layer count (999 = all), not "auto" | "auto" is not a numeric layer count; the canonical llama.cpp idiom for full offload is a large integer. The value was never exercised while the CPU build ignored it |
| D-096 | `parallel` stays 1; node-level request concurrency is deferred | `--parallel N` splits the context window N ways and only pays off when a node receives concurrent requests. The scheduler deliberately leases one job per node (D-009), so raising it today would reduce usable context for zero gain. Revisit together with multi-lease scheduling when concurrent demand exists |
| D-097 | Added 14B and 32B model tiers priced above the 7B tier | Host economics scale with what a card can hold: a 24GB host serving 32B earns several times what an 8GB host serving 7B earns per node-hour, at prices still ~25% under typical hosted rates. Same Apache-2.0 license family and the same pinned-GGUF provenance method as the 7B manifests |
